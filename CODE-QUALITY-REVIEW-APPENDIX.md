EVERYTHING SUCCEEDS: the native installer runs (:30), the binary lands at ~/.local/bin/claude, the AGT-02b version-lock passes, "claude-code: install complete" is printed at :53. THEN jq at :65 hits the parse error and the script dies. The user sees `parse error: Expected another key-value pair at line 12, column 3` with NO mention of settings.json, no mention of claude-code, and no suggestion to fix their config — followed by a generic install failure. Claude Code IS installed and works; AgentLinux records the install as failed. Every retry adds another settings.json.tmp.NNN, and the auto-updater is never disabled, so ADR-011's version pin is silently unenforced at runtime.
   RELATED, SMALLER: codex/install.sh:94-99 runs apt-get update and apt-get install bubblewrap with >/dev/null 2>&1 on BOTH, so the non-fatal "could not install bubblewrap via apt" carries no apt error text and no exit code — undiagnosable from a pasted log.
   FIX: `trap 'rm -f "$tmp"' EXIT` (codex/install.sh:132 already models this correctly), and pre-validate with `jq empty "$settings_file"` so the message can say which file is malformed.

10. MEDIUM-LOW — Chrome package download: ~110MB, unbounded, into the agent's HOME, cleaned only by a RETURN trap. plugin/catalog/lib/browser-deps.sh:84-85, :96, :104. A RETURN trap fires when the FUNCTION returns normally. It does NOT fire when the shell is killed by SIGINT/SIGTERM, and does not fire if the sourcing recipe's set -e terminates the process from inside a nested call.
    SCENARIO: `agentlinux install playwright-cli` on a slow link. The unbounded 110MB download starts at :96; after minutes with no progress output the user hits Ctrl-C. The RETURN trap never runs, and a partial ~/.chrome-agentlinux.abc123.deb (say 60MB) is left in the agent's home. Two more retries → three orphaned partials, ~200MB, dotfile-named so the user never notices. No cleanup path exists: al_browser_ensure_chrome mktemps a fresh name each run, and `agentlinux remove playwright-cli` has no knowledge of them.
    (The unpinned rolling-Chrome trust model is explicitly documented and accepted at :87-93 — not flagged; the leak and the missing timeout are separable.)

11. LOW — `exec` at the end of the installer BYPASSES the EXIT trap: the downloaded tarball is leaked in /tmp on every SUCCESSFUL install. packaging/curl-installer/install.sh:185 (`trap "rm -rf '${tmpdir}'" EXIT`), :250 (`exec "$exe" provision …`). exec replaces the process image; bash traps do not run. The trap correctly cleans up on every FAILURE path, and the header at :30 advertises it as "info-disclosure hygiene" — but the happy path skips it. Every successful `curl … | sudo bash` leaves /tmp/agentlinux-install.XXXXXX/ containing the full release tarball plus its sidecar, root-owned, permanently. On machines where /tmp is not a tmpfs (many cloud images) that is tens of MB per install, accumulating across RC bumps.
    FIX: rm -rf "$tmpdir" immediately before the exec.

12. LOW — The Playwright browser-launch probe bounds `open` but not `close`. plugin/catalog/agents/playwright-cli/install.sh:121-126. `timeout 90 playwright-cli open about:blank` then an UNGUARDED `playwright-cli close`, both with all output discarded.
    SCENARIO: open succeeds (a headless Chrome now holds the agentlinux-install session). close hangs — unresponsive browser under a memory-constrained container, or a stale session socket. The install blocks indefinitely with no output; the user sees a frozen install and a Chrome process eating memory. Ctrl-C orphans the browser and leaves the session file, so the NEXT open may inherit the same stale session. And when the probe legitimately fails, :124 says "browser launch probe failed after dependency installation" with the actual Playwright stderr thrown away — the user cannot tell a missing libnss3 from a sandbox denial, exactly the class this probe exists to catch.

WHAT IS ROBUST (RL3):
- The integrity chain in the curl-installer is correct and correctly ORDERED. install.sh:210-220 asserts gzip magic, then sha256sum -c, then extracts — verify strictly before execute, with a specific error for the 404-as-HTML case a bare checksum mismatch would obscure. Truncation cannot masquerade as success. plugin/catalog/lib/prebuilt-binary.sh:74-136 mirrors the discipline, and its `awk '$2==a'` exact-filename match closes the near-name-collision hole grep -E would leave open.
- main(){...}; main "$@" partial-download safety (install.sh:9-15, :253) is the right mitigation, correctly implemented with nothing after the final call.
- set -euo pipefail is UNIVERSAL across the installer, build script, all four Docker/QEMU harnesses, and every agents/*/install.sh and uninstall.sh. The sourced lib/*.sh deliberately omit it and instead return non-zero from every function — a documented, consistently applied choice.
- QEMU harness cleanup is EXEMPLARY: boot.sh:306-327 traps EXIT/INT/TERM, escalates TERM→KILL with a grace loop, reaps the pid, and copies the serial log to the artifacts dir BEFORE tearing down RUN_DIR — all on the failure path. selftest_checksum_guard at :83-102, which proves the verification code actually rejects a flipped byte on EVERY run, is a genuinely unusual and good idea.
- Idempotency is thought through where it matters. NO recipe appends to an rc file unguarded — the only two `>>` in the whole catalog are codex/install.sh:134 (cat into a fresh temp, then atomic mv, mode preserved via chmod --reference) and mcp-register.sh:156 (marker-delimited block preceded by an unconditional deregister that strips any prior block). The claude leg is remove-then-add. _al_mcp_json_set is mktemp-in-destination-dir + mv, so JSON config writes are atomic.
- Marker-gated ownership in uv-bootstrap.sh:139-167 and daemon-lifecycle.sh:140-162 — never revert linger or delete a uv the user brought, and treat "could not list tools" as KEEP, not DELETE. The right default on an ambiguous read.
- The QEMU provisioner-identity guard (boot.sh:548-592) refuses to run the gate unless it can POSITIVELY PROVE the artifact is a static musl ELF, and refuses if none of readelf/file/ldd is available rather than assuming.
- nightly-mutation.yml's continue-on-error: true is deliberate and documented as advisory, with the enforcing gate in test.yml's --in-diff run — including the --relative fix at test.yml:184-191 that closes a real false-green. NOT a finding.
